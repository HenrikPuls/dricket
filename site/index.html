People and agents work from the same queue. A protocol decides who takes what.

dricket is that protocol. Claiming a ticket works like pushing to Git: the first push wins, and everyone else is told right away to pick something else. If a runner crashes, its claim runs out by itself. If it keeps working anyway, its next save is rejected. Your Git host already does all of this, so there is no server to run. Tickets are plain Markdown files you can open in any editor, and dk is the small tool that keeps everyone honest.

Why

Tracking work was never the hard part.

Duplicate work

Two runners pick the same task and both finish it. You find out when the second pull request arrives.

Claims that never die

A crashed agent holds its task forever. A lock file has no expiry date.

Nothing says stop

An agent that lost its task just keeps writing, unless something tells it to stop.

A service to babysit

The usual fix is a coordination server: one more thing to install, update and watch.

How it works

The fast-forward is the lock.

1 · refresh

Runner A reads the tickets as they are right now.

2 · commit

A adds its claim on top: its name and how long it needs.

3 · publish

Git lets exactly one update through. First push wins.

4 · retry

B is too late. B reads again, sees the ticket belongs to A, and picks something else.

Git is just the carrier. The full rules for claims, retries and error codes are written down in docs/protocol.md.

No server to run

Your Git host stores the tickets and decides every claim. Nothing else to install, update or watch.

Markdown you can edit

One folder per ticket, comments in their own files, history in git log. Open it in any editor.

Names you can say out loud

app-6842 is easy to drop into a conversation. And a ticket's file never moves when its status changes.

One tool for everyone

People and agents make their changes through dk, so the files never end up broken.

Guardrails for collaboration

Built for runners that crash, stall and lose a claim.

Sstarts at 2 h
Mstarts at 8 h
Lstarts at 24 h, the default

Starting values you can change. Our stress test checks that the rules hold, not how fast a real host answers.

Claims come in sizes

You pick S, M or L instead of guessing hours. If you need more time, you say why.

Lost claims stop themselves

Every claim bumps a counter. A runner holding an old count gets its next save rejected, and knows it is time to stop.

People keep the last word

Everyone with write access is a teammate. Agents hand their work over at review; a person marks it done.

Rules over trust

A ticket's identity can never change, and every update has to follow the rules or it is rejected.

Your work is never lost

You can only publish on top of the version you started from. If someone beat you to it, your local changes stay put.

Comments never collide

Comments live in their own files, so they never clash with the owner's edits. dk inbox shows what came in.

A session

Edit the file. Publish with confidence.

$ dk claim app-1 --size M
claimed app-1 (epoch 1, lease until …)
$ dk sync
synced tickets
$ $EDITOR tickets/app/0000/app-1/ticket.md
$ dk inbox app-1
comment … henrik: please check the empty-password case
$ dk commit app-1
committed app-1 (rev 2, commit …)
$ dk release app-1 --stage review -m "Fix on dk/app-1"
released app-1 -> review

A real session from the development branch. Times and commit IDs shortened.

Trust and integrity

Everyone trusted can write. The rules keep things consistent.

What dk checksWhat your Git host handlesWhat nobody promises
Every file stays readable, a ticket's identity never changes, every update follows the rules, and your local work survives a conflict. Logins, tokens and who is allowed to push. Anyone who can push is treated as a trusted teammate. Proof that someone really is who they say, exact clocks, or stopping an agent from doing things outside Git.

dk never blindly trusts what a ticket says, and a comment never interrupts a runner mid-work.
